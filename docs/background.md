# 背景と決定事項

要件定義（[requirements.md](requirements.md)）の判断の理由をまとめる。

## 実装の方針：Deno を子プロセスとして使う

Node.js から Deno を子プロセスとして起動し、Deno の権限フラグでファイル・通信を制限する。Deno は利用者に見せない実装の詳細として扱う。

選んだ理由：

- Deno の権限チェックはランタイムの中で行われ、OS の機能（namespace、seccomp、root）に依存しない。microVM やコンテナの中でもそのまま動く
- ファイルはパス単位（読み取り・書き込みを別々に）、通信はホストとポート単位で許可できる
- npm パッケージをそのまま使える

ほかの候補を選ばなかった理由：

| 候補 | 選ばなかった理由 |
|---|---|
| Node.js の Permission Model | 通信をドメイン単位で制御できない |
| isolated-vm | 同じプロセスで動くため巻き込まれて落ちる。ファイルや通信をすべて自前で注入する必要があり、npm がそのまま使えない |
| QuickJS などの WASM | npm のエコシステムが使えず、遅い |
| マネージドなサンドボックス（AgentCore Code Interpreter など） | 分離が強すぎて、ホストのファイルを見せたり、通信先をドメイン単位で許可したりできない |
| OS の機能を使う OSS のサンドボックス | VM やコンテナの中では動かないものが多い |

## 分離の考え方：二段構え

- 外側の境界は VM（AgentCore Runtime の microVM など）。ランタイムの脆弱性を突いた脱出はここで止める
- 内側の境界は Deno の権限。同じ VM にあるホストプロセスの秘密情報（環境変数、IAM 認証情報、メタデータのエンドポイント）を、LLM の書いたコードから守る

このため、Deno に次の権限は与えない：`--allow-run`、`--allow-ffi`、`--allow-sys`、`--allow-env`、`--allow-all`。どれか一つでも与えると、権限による制限が意味をなさなくなる。

## 決定事項とその理由

| 決定 | 理由 |
|---|---|
| 実行は 1 回ずつ独立させ、作業ディレクトリのファイルだけを引き継ぐ | LLM は 1 回で完結するスクリプトを書くのが得意。プロセスが落ちても状態で混乱しない。Deno の権限は起動時に決まるので、実行ごとに許可を変えるにはプロセスを分ける必要がある |
| `code` のほかに `entrypoint`（作業ディレクトリ内のファイル）でも実行できる | LLM がファイル編集ツールでコードを書いて直し、実行だけをツールとして呼ぶ使い方が多いため |
| 書き込めるのは作業ディレクトリだけ。読み取り専用のパスは別に指定できる | 入力データをコピーせずに見せつつ、壊されないようにする。書き込み先を一か所にすると、LLM もホストも出力を追いやすい |
| 使うパッケージは import から割り出し、許可リストで制限できる | LLM はコードを書くだけで済む。開発者は使えるパッケージを絞れる |
| パッケージの取得とコードの実行を別の段階に分ける | registry への通信を、ユーザーのコードからデータの持ち出しに使わせない |
| 戻り値は返さず、標準出力・標準エラー・終了コードを返す | LLM は結果を `console.log` で出すのが自然 |
| ホストの関数をサンドボックスから呼ぶ機能は初版では作らない | 主な用途（データの加工やファイルの生成）には要らない。必要になったら、プロセス間通信で JSON をやり取りする形で足せる |
| Node.js ライブラリとして提供し、MCP 化は考えない | 今の利用者は Node.js でエージェントを作る開発者 |
| Python は初版では扱わない | まず JS / TS で仕組みを固める |

## 次にやること

- 設計：Node と Deno の受け渡し、パッケージの許可リストの検査方法、通信の制御方法（Deno の `--allow-net` か egress プロキシか）
- PoC：AgentCore Runtime 上で Deno の権限による制限が効くこと、実行時に決まる import やキャッシュ経由で許可リストを回避できないことを確かめる
